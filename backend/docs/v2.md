# Paladin v2 — Architecture & Migration

v2 is a clean-break redesign of the Paladin Connect API. Backward compatibility
is not provided — v1 will be removed once v2 is fully wired.

## What changed

| Area | v1 | v2 |
|---|---|---|
| ObjectTags | First-class `ObjectTagService` with slugs | **Removed.** Use prefixes + tags. |
| Tenant identity | In every request body | **From JWT claim only** (except `TenantService`) |
| Object addressing | Dual (`object_id` OR `collection+key`) | **Single** — resource name `collections/{c}/objects/{id}` |
| Move semantics | `MoveObject` RPC (copy+delete server-side) | **Removed.** Client does Copy → Delete. |
| Upload completion | Triadic: Upload → PUT → Complete | **Capability-driven:** `CompletionMode` advertised in response. Event-driven when available. |
| Filters | Hard-coded `AND` fields | **CEL expressions** (AIP-160) |
| Batch ops | Sync, max 1000 items | **Async LRO** (AIP-151), no cap, via filter |
| Collection provisioning | IAM/S3 create-bucket | **Logical namespace** (Postgres row) |
| Authorization | Ad-hoc service checks | **Cedar** policy engine |
| Pagination | `total_count` in every response | **Removed.** `CountObjects` RPC is explicit. |
| `UPLOADING` state | Separate state | **Removed.** PENDING → AVAILABLE/FAILED only. |
| HTTP + Connect | `google.api.http` on every RPC | **Connect-only.** One transport. |
| Streaming | Not supported | **`UploadSmall`** stream for <1 MiB payloads. |

## Authorization model (Cedar)

The Cedar schema is in [policies/schema.cedarschema](../policies/schema.cedarschema).
Per-tenant inherited policy and per-collection policy are concatenated and
compiled into a cached `PolicySet`. Decisions take ~100 µs on the hot path.

**Evaluation sites:**

- `ObjectService.UploadObject` → action `PresignPut` (before issuing the presign)
- `ObjectService.DownloadObject` → action `PresignGet`
- `ObjectService.DeleteObject` → action `DeleteObject`
- (etc. — see `internal/policy/cedar.ActionXxx`)

**Invariant:** `forbid` rules always win over `permit`. The default policy template
includes a structural `forbid` that blocks cross-tenant writes as a defense in depth.

## Completion modes

`CompletionMode` is a **property of the storage backend**, advertised to the client
in `UploadObjectResponse`:

- **IMPLICIT** — backend supports events (AWS S3 → SNS/SQS). The server's event
  consumer promotes `PENDING → AVAILABLE` without client involvement.
  Client *may* call `CompleteObject` for read-your-writes; it's a no-op when the
  event has already arrived.
- **EXPLICIT** — backend has no reliable events (MinIO w/o notify, SeaweedFS).
  Client **must** call `CompleteObject`. Reconciler is still running as a safety net.

The state machine is identical in both modes. The only difference is *who* triggers
the transition; the transition itself is idempotent (see `internal/statemachine/object.go`).

## Reconciler

Runs in both modes. For `EXPLICIT` collections it's the primary safety net; for
`IMPLICIT` it's a tertiary fallback behind event delivery.

Per-tick logic:

1. Scan `objects_v2 WHERE state = 'PENDING' AND presign_expires_at < now() - grace`.
2. For each, HEAD the backend:
   - If exists → `PromoteToAvailable(source=reconciler)`.
   - If 404 → `MarkFailed`.

Metric to watch: `paladin_object_transitions_total{source="reconciler",target="AVAILABLE"}` —
when this exceeds 5% of total AVAILABLE transitions, the events pipeline has
degraded.

## Resource names

Follows AIP-122:

- `tenants/{tenant_id}`
- `collections/{collection}` (tenant implicit from auth)
- `collections/{collection}/objects/{object_id}`
- `operations/{operation_id}`

Path-based lookup (when external tools only know the S3 key) is a dedicated
RPC: `ObjectService.LookupObject(collection, key) → Object`. Everything else uses
the resource name.

## Long-running operations

All batch and forceful-delete RPCs return `operations/{id}`. Poll with
`OperationService.GetOperation` or stream with `WatchOperation`. See
[proto/paladin/v2/operation_service.proto](../proto/paladin/v2/operation_service.proto).

## Migration path

1. **Apply migration 025** — creates `*_v2` tables, enums, triggers in parallel
   with v1 tables. Zero-downtime.
2. **Deploy v2 stack** on a separate Connect endpoint (e.g. `/paladin.v2.*`).
   Both v1 and v2 serve traffic during migration.
3. **Clients switch** to v2 endpoints. v1 metric `requests_total` declines.
4. **Backfill** — copy rows from `objects` → `objects_v2` (one-shot script,
   preserving `object_id`; object keys become tags via a deterministic mapping).
5. **Remove v1** — drop v1 routes, then drop v1 tables in a follow-up release.
