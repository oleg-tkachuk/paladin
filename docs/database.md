# Database

The `paladin` uses PostgreSQL as its primary metadata and operational data store. No object binary data is stored in the database; it holds only the metadata orchestrating the S3-compatible backend.

- **DB Type:** PostgreSQL 15+ (requires JSONB)
- **Driver:** `pgx/v5`
- **Connection Logic:** Connection pooling is configured via `pgxpool`, governed by the `datastores.postgres.pool` config (managing `max_conns`, `min_conns`, `max_conn_lifetime`, `max_conn_idle_time`).
- **Migration Tool:** `goose/v3` (migrations are located in `/migrations`).
- **Data Access:** Code generated by `sqlc/v1.30.0`.

## 1. Schema Overview

The database is highly multi-tenant. All significant tables employ PostgreSQL **Row-Level Security (RLS)** to enforce strict isolation. A transaction opening must set the local variable `app.tenant_id` to read or modify any tenant data.

### 1.1 `objects`

Core metadata tracker for any single or multipart upload.

- **Purpose**: Record location, state, and client-provided metadata of an object blob.
- **PK**: `id` UUID.
- **Key Columns**:
  - `tenant_id` (TEXT): Tenant isolation boundary.
  - `object_key` (TEXT): The canonical path in S3.
  - `category` (TEXT) & `subpath` (TEXT): Used to auto-derive `object_key`.
  - `status` (TEXT): `pending`, `uploading`, `uploaded`, `complete`, `aborted`, `error`, `soft_deleted`, `hard_deleted`.
  - `labels` (JSONB): Dynamic key-value pairs for flexible filtering.
  - `external_ref` (TEXT): User-supplied identifier linking to external systems.
- **Constraints**:
  - `object_key` generation is strictly enforced via DB trigger (`trg_objects_enforce_key`): `tenant_id/category[/subpath]/id`.
  - `status` strictly checked by `chk_objects_status`.
- **Indexes**:
  - `idx_objects_tenant_created_at` (tenant_id, created_at DESC)
  - `uq_objects_tenant_key` UNIQUE (tenant_id, object_key)
  - `uq_objects_tenant_external_ref` UNIQUE (tenant_id, external_ref)
  - `idx_objects_labels` GIN (labels)
  - Several composite indexes for category-based filtering.
- **RLS**: Enabled `(tenant_id = current_setting('app.tenant_id'))`.

### 1.2 `object_categories`

- **Purpose**: Strict vocabulary for organizing objects and constructing keys.
- **PK**: `id` UUID.
- **Key Columns**: `tenant_id`, `slug`, `name`.
- **Constraints**: `slug` must match regex `^[a-z0-9][a-z0-9_-]{0,62}$`. UNIQUE on `(tenant_id, slug)`.
- **RLS**: Enabled.

### 1.3 `multipart_uploads`

- **Purpose**: Control-plane state tracking for S3 multipart upload processes.
- **PK**: `id` UUID.
- **Key Columns**:
  - `object_id` UUID: FK to `objects(id)` `ON DELETE CASCADE`.
  - `upload_id` TEXT: The S3 provider's upload ID.
  - `status` TEXT: `initiated`, `completed`, `aborted`, `expired`, `uploaded`.
- **Indexes**: UNIQUE `(tenant_id, upload_id)`.
- **RLS**: Enabled.

### 1.4 `multipart_parts`

- **Purpose**: Optional granular tracking of individual parts (ETags, sizes) associated with an upload.
- **PK**: `(multipart_id, part_number)`.
- **RLS**: Enabled recursively `(multipart_id IN (SELECT id FROM multipart_uploads))`.

### 1.5 `audit_logs`

- **Purpose**: Immutable history of control-plane API access, particularly for security and compliance.
- **PK**: `id` UUID.
- **Key Columns**: `tenant_id`, `actor_type`, `method`, `path`, `request_id`, `http_status`.
- **Indexes**: Highly optimized for tenant-based time-series queries.
- **RLS**: Enabled.

### 1.6 `idempotency_keys`

- **Purpose**: Safe retries of state-mutating HTTP operations.
- **PK**: `(tenant_id, idempotency_key)`.
- **Key Columns**: `request_hash`, `response_body`, `expires_at`.
- **RLS**: Enabled.

## 2. Transactions

- **Boundaries**: Transactions strictly start at the HTTP handler layer or application `internal/service` layer where unit-of-work abstractions exist.
- **Isolation**: Follows logical PostgreSQL default (Read Committed) unless explicitly elevated for race-condition prevention (like Complete Multipart operations).
- **Tenant Context**: Every transaction is wrapped with an initialization step executing `SET LOCAL app.tenant_id = '...'` to satisfy RLS policies.

## 3. Data Lifecycle

- **Soft Delete vs Hard Delete**:
  - Normal DELETE API calls issue a **soft delete**: updating `objects.status` to `soft_deleted` and setting `deleted_at`. S3 content remains unchanged.
  - A purge API call issues a **hard delete**: executing an actual SQL `DELETE`, which cascades to multipart records. The underlying S3 blob is also deleted.
- **Cleanup Jobs (Reaper Worker)**:
  - Background asynchronous jobs periodically sweep the system.
  - `soft_deleted` objects exceeding retention (`pending_ttl`) are automatically purged from S3 and hard deleted from PostgreSQL.
  - Uploads stuck in `pending` or `initiated` states that exceed timeouts are automatically aborted.
- **Audit Logs**: Governed by `audit_log_ttl` threshold, pruned periodically by a Reaper-equivalent background process to prevent unbounded growth.
